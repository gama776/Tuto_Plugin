Analyse Dynamique

Observer et instrumenter un programme Java pendant son exécution : Agent Java, transformation du bytecode avec ASM, mesure d'affectations et intégration dans l'IDE.

Section 1

Panorama des approches d'analyse dynamique

L'analyse dynamique consiste à recueillir des métriques et des événements lors de l'exécution effective du programme.

ApprochePrincipePoints fortsLimites
Agent Java + ASM (Notre choix SAE) Instrumentation sur mesure du bytecode lors du chargement des classes par la JVM. Contrôle total : enregistre ce qu'on veut (affectations, valeurs, compteurs d'exécution, traces de méthodes). Demande la maîtrise d'ASM et du bytecode ; gestion fine de la pile JVM.
Byte Buddy / Javassist Bibliothèques de plus haut niveau pour abstraire les instructions bytecode. Syntaxe plus simple pour intercepter l'entrée ou la sortie de méthodes. Moins adaptées aux manipulations d'instructions élémentaires (affectations locales, opcodes d'injection précis).
JDI (Java Debug Interface) Pilotage d'une JVM distante par socket de debug. Ne modifie pas le bytecode de l'application cible. Surcharge importante (ralentissement majeur) pour du traçage continu.
API Debugger IntelliJ (XDebugger) Accrochage aux sessions de débogage de l'IDE. Accès aux variables locales et à la pile aux points d'arrêt dans l'interface de l'IDE. Non conçu pour collecter automatiquement des métriques d'exécution complètes.
Java Flight Recorder (JFR) Module de profilage bas niveau intégré au runtime de la JVM. Impact quasi nul sur les performances. Orienté métriques système/mémoire/CPU, pas analyse fine des variables ou instructions.
Section 2

Statique vs Dynamique — L'idée centrale

Il est fondamental de bien distinguer le code source Java, le bytecode .class et l'exécution runtime au sein de la JVM.

JavaExemple d'affectations et boucles
int total = 0;           // 1 site d'affectation statique
for (int i = 0; i < 5; i++) { // 2 sites statiques (i = 0, i++)
    total += i;           // 1 site statique (total += i)
}
📖

Analyse Statique (PSI)

Analyse le code sans l'exécuter via l'AST/PSI d'IntelliJ :

Source Java → Arbre PSI → Inspection visuelle IDE

Compte le nombre de variables et d'instructions déclarées dans les fichiers (ex. 4 sites d'affectation statiques dans le code).

▶️

Analyse Dynamique (Agent + ASM)

Observe le comportement réel en mémoire pendant la chaîne de compilation et d'exécution :

.class → Agent Java + ASM → JVM Runtime → Traces & Métriques

Mesure le nombre effectif de passages sur ces instructions (ex. total += i s'exécute 5 fois en dynamique).

Deux grandes manières d'observer en dynamique

Instrumentation Bytecode (Agent Java)

On modifie les octets du bytecode au moment du chargement par la JVM pour insérer des appels d'enregistrement :

Counters.hit(idAffectation);

Exécution rapide, automatique et totalement transparente pour l'application cible.

Supervision Debugger (JDI)

Le bytecode reste intact, mais la JVM envoie des événements via le protocole JDWP à chaque point d'arrêt ou pas à pas.

Pratique pour l'inspection interactive, mais trop lent pour un suivi exhaustif et continu d'affectations.

Section 3

Agent Java — Concept & Architecture

🚀

Chargement JVM

Un Agent Java est un fichier JAR spécifié à la JVM via l'argument CLI -javaagent:agent.jar=options avant l'appel à main().

🔧

Point d'entrée Premain

La méthode premain(String args, Instrumentation inst) est exécutée en premier. L'objet Instrumentation permet d'enregistrer un ClassFileTransformer.

📄

Manifeste JAR

Le fichier MANIFEST.MF doit déclarer : Premain-Class: fr.monequipe.agent.TraceAgent et Can-Retransform-Classes: true.

Kotlin agent/build.gradle.kts — Configuration du JAR Fat avec ASM 
tasks.jar {
    manifest {
        attributes(
            "Premain-Class" to "fr.monequipe.agent.TraceAgent",
            "Can-Retransform-Classes" to "true"
        )
    }
    // Emballer les dépendances (ASM) dans le JAR de l'agent (Fat JAR)
    from(configurations.runtimeClasspath.get().map { if (it.isDirectory) it else zipTree(it) })
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
}
Java TraceAgent.java & TraceTransformer.java 
package fr.monequipe.agent;

import java.lang.instrument.ClassFileTransformer;
import java.lang.instrument.Instrumentation;
import java.security.ProtectionDomain;
import org.objectweb.asm.ClassReader;
import org.objectweb.asm.ClassWriter;

public final class TraceAgent {
    public static void premain(String agentArgs, Instrumentation inst) {
        System.out.println("[AGENT] Initialisation de l'agent d'instrumentation...");
        inst.addTransformer(new TraceTransformer(agentArgs), false);
    }
}

final class TraceTransformer implements ClassFileTransformer {
    private final String targetPrefix;

    TraceTransformer(String targetPrefix) {
        this.targetPrefix = targetPrefix == null ? "" : targetPrefix.replace('.', '/');
    }

    @Override
    public byte[] transform(ClassLoader loader, String className, Class<?> classBeingRedefined,
                             ProtectionDomain protectionDomain, byte[] classfileBuffer) {
        // Ignorer les classes système ou hors du package cible
        if (className == null || !className.startsWith(targetPrefix)) {
            return null; // null signifie "pas de modification"
        }
        try {
            ClassReader cr = new ClassReader(classfileBuffer);
            ClassWriter cw = new ClassWriter(cr, ClassWriter.COMPUTE_MAXS);
            cr.accept(new InstrumentingClassVisitor(cw), 0);
            return cw.toByteArray();
        } catch (Throwable t) {
            System.err.println("[AGENT ERROR] Erreur lors de la transformation de " + className);
            t.printStackTrace();
            return null;
        }
    }
}

3 Règles d'hygiène fondamentales pour les Agents Java

1

Filtrer rigoureusement les packages

Ne jamais instrumenter le JDK (java/, javax/, sun/, jdk/) ni le package interne de l'agent. Une tentative d'instrumentation des classes système provoque un ClassCircularityError ou un crash JVM.

2

Capturer tous les Throwable dans transform()

Si une exception est levée pendant le travail d'ASM dans transform(), la JVM l'avale silencieusement et la classe originale est chargée non modifiée sans aucun avertissement. Le try/catch (Throwable t) est impératif.

3

Garantir le Thread-Safety et minimiser l'impact

Les méthodes injectées (ex. Counters.hit(id)) sont appelées en boucle dans des environnements multithread. Utiliser LongAdder ou des tableaux atomiques pour éviter les goulots d'étranglement.

1

Instructions Bytecode cibles pour l'analyse des affectations

Pour suivre l'écriture dans des variables en Java, ASM recherche les opcodes d'écriture suivants :

ISTORE, LSTORE, FSTORE, DSTORE, ASTOREÉcriture dans une variable locale (int, long, float, double, objet/ref) IINCIncrémentation directe d'une variable locale (ex: i++) PUTFIELDÉcriture dans un attribut d'instance (this.champ = val) PUTSTATICÉcriture dans un attribut statique de classe (Classe.champ = val)
2

Architecture en Deux Passes

Passe 1 : Analyse & Recensement

Parcourir la méthode pour repérer chaque instruction d'affectation et attribuer un identifiant unique ID. On extrait le nom de la variable sans modifier le flux d'instructions.

Passe 2 : Injection de la Sonde

Pour chaque affectation identifiée, injecter immédiatement après l'instruction l'appel statique de comptage :
LDC id (Empiler l'ID)
INVOKESTATIC fr/monequipe/agent/Counters.hit(I)V

3

Résolution du nom des variables locales via la LocalVariableTable

Dans le bytecode, les variables locales sont désignées par un index numérique (slot, ex: ISTORE 2). Pour associer le slot 2 au nom source compteur, ASM consulte la table des variables locales :

Slot (index 2) + Offset instruction
→
LocalVariableTable
→
Nom source : compteur

⚠️ Prérequis : Le code cible doit être compilé avec les symboles de débogage (option javac -g).

5

Mesure Statique vs Mesure Dynamique

📊 Mesure Statique (Sites)

Compte le nombre d'instructions d'affectation présentes physiquement dans le bytecode.
val = 10; val = 20; val++; → 3 sites d'affectation

⚡ Mesure Dynamique (Exécutions)

Compte le nombre de fois où ces instructions ont réellement été exécutées durant la session.
Si le bloc est appelé 100 fois → 300 exécutions d'affectations

Synthèse pour la soutenance orale (6 points clés)

  1. 1

    Chargement Premain

    La JVM charge l'agent via -javaagent avant d'exécuter la méthode main().

  2. 2

    Transformation

    L'agent intercepte les classes cibles via un ClassFileTransformer.

  3. 3

    Analyse ASM

    ASM parcourt le bytecode et identifie les opcodes d'affectation (STORE, PUTFIELD, etc.).

  4. 4

    Injection d'instructions

    L'agent injecte un appel statique Counters.hit(id) après chaque site d'affectation.

  5. 5

    Collecte Runtime

    Pendant l'exécution, les compteurs en mémoire s'incrémentent à chaque passage.

  6. 6

    Restitution IDE

    Le fichier de résultats TSV est analysé et présenté dans le plugin IntelliJ.

Section 5

ASM en détail — Manipulation du Bytecode

ASM est le framework standard de manipulation directe du bytecode Java. Il s'appuie sur le Visitor Pattern avec une chaîne de traitement réentrante : ClassReader → ClassVisitor → ClassWriter.

Composant ASMRôle et Description
ClassReaderLit le tableau d'octets du fichier .class et émet les événements de visite vers le ClassVisitor.
ClassVisitorIntercepte les déclarations de la classe : visit(), visitField(), visitMethod(), visitEnd().
MethodVisitorIntercepte les instructions à l'intérieur d'une méthode : visitVarInsn(), visitFieldInsn(), visitMethodInsn(), visitLdcInsn().
ClassWriterReconstruit et génère le nouveau tableau d'octets (byte[]) à partir des visites.
AdviceAdapterSous-classe évoluée de MethodVisitor offrant les déclencheurs onMethodEnter() et onMethodExit().
OpcodesInterface contenant toutes les constantes du bytecode (ex: ASM9, INVOKESTATIC, ISTORE, ACC_PUBLIC).
TypeHelper pour manipuler les descripteurs de types JVM (ex: Type.INT_TYPE, Type.getDescriptor(String.class)).
Java InstrumentingClassVisitor.java — Injection ASM complète avec AdviceAdapter 
package fr.monequipe.agent;

import org.objectweb.asm.*;
import org.objectweb.asm.commons.AdviceAdapter;

final class InstrumentingClassVisitor extends ClassVisitor {
    private String className;

    InstrumentingClassVisitor(ClassVisitor next) {
        super(Opcodes.ASM9, next);
    }

    @Override
    public void visit(int version, int access, String name, String signature,
                       String superName, String[] interfaces) {
        this.className = name;
        super.visit(version, access, name, signature, superName, interfaces);
    }

    @Override
    public MethodVisitor visitMethod(int access, String name, String descriptor,
                                       String signature, String[] exceptions) {
        MethodVisitor mv = super.visitMethod(access, name, descriptor, signature, exceptions);
        if (mv == null || (access & (Opcodes.ACC_ABSTRACT | Opcodes.ACC_NATIVE)) != 0) {
            return mv;
        }

        return new AdviceAdapter(Opcodes.ASM9, mv, access, name, descriptor) {

            @Override
            public void visitVarInsn(int opcode, int varIndex) {
                // 1. Exécuter l'instruction d'affectation originale (ex: ISTORE)
                super.visitVarInsn(opcode, varIndex);

                // 2. Détecter si c'est un Opcode d'écriture (ISTORE, LSTORE, FSTORE, DSTORE, ASTORE)
                if (opcode >= Opcodes.ISTORE && opcode <= Opcodes.ASTORE) {
                    int siteId = Counters.register("LOCAL", className, name, "slot_" + varIndex);
                    // Injecter : LDC siteId puis INVOKESTATIC Counters.hit(I)V
                    visitLdcInsn(siteId);
                    visitMethodInsn(Opcodes.INVOKESTATIC, "fr/monequipe/agent/Counters",
                                    "hit", "(I)V", false);
                }
            }

            @Override
            public void visitFieldInsn(int opcode, String owner, String fieldName, String fieldDesc) {
                super.visitFieldInsn(opcode, owner, fieldName, fieldDesc);
                if (opcode == Opcodes.PUTFIELD || opcode == Opcodes.PUTSTATIC) {
                    int siteId = Counters.register("FIELD", owner, fieldName, fieldName);
                    visitLdcInsn(siteId);
                    visitMethodInsn(Opcodes.INVOKESTATIC, "fr/monequipe/agent/Counters",
                                    "hit", "(I)V", false);
                }
            }
        };
    }
}

Pièges courants et bonnes pratiques ASM

Piège ASMCause & Solution
ClassFileFormatError / VerifyError Déséquilibre dans la pile d'exécution. Si une valeur est poussée sur la pile (ex: visitLdcInsn), elle doit être consommée immédiatement par l'instruction suivante (ex: hit(I)V).
COMPUTE_FRAMES vs COMPUTE_MAXS COMPUTE_FRAMES recalcule automatiquement les StackMapTable (Java 7+), mais peut lever une ClassNotFoundException dans le contexte du ClassLoader d'un agent. Privilégier COMPUTE_MAXS lorsque vous n'ajoutez pas de branchements conditionnels.
Version d'ASM incompatibleSi la cible utilise Java 17 ou Java 21, il faut utiliser Opcodes.ASM9 et ASM 9.5+. Sinon une IllegalArgumentException: Unsupported class file major version survient.
Purger le constructeur <init>Ne jamais insérer de code d'observation avant l'appel obligatoire à super() dans un constructeur. AdviceAdapter gère ce cas automatiquement via onMethodEnter().
Section 6

Lancer le programme avec l'agent depuis l'IDE

Comment le plugin IntelliJ fait-il exécuter l'application cible avec le paramètre -javaagent ? Deux approches sont possibles.

Option A Processus indépendant via GeneralCommandLine Lancement Manuel

Le plugin instancie lui-même la commande système pour démarrer une nouvelle JVM. Nécessite de calculer manuellement le chemin du JDK et du Classpath.

Java 
GeneralCommandLine cmd = new GeneralCommandLine(javaExePath)
        .withParameters("-javaagent:" + agentJarPath + "=com.example.app",
                         "-cp", targetClasspath, mainClass)
        .withWorkDirectory(project.getBasePath());

OSProcessHandler handler = new OSProcessHandler(cmd);
handler.addProcessListener(new ProcessAdapter() {
    @Override
    public void processTerminated(@NotNull ProcessEvent event) {
        // Lire le fichier TSV produit par l'agent à la fin du processus
        DynamicReportService.getInstance(project).loadReport();
    }
});
handler.startNotify();
Option B Integration transparente via JavaProgramPatcher ⭐ Recommandé

Le plugin se greffe sur les exécutions standards de l'IDE (bouton Run/Debug de l'utilisateur) et injecte le paramètre -javaagent directement dans la JVM lancée par IntelliJ.

Java AgentProgramPatcher.java 
package fr.monequipe.sae.dynamic;

import com.intellij.execution.Executor;
import com.intellij.execution.configurations.JavaParameters;
import com.intellij.execution.configurations.RunProfile;
import com.intellij.execution.runners.JavaProgramPatcher;

public class AgentProgramPatcher extends JavaProgramPatcher {
    @Override
    public void patchJavaParameters(Executor executor, RunProfile configuration, JavaParameters params) {
        String agentPath = AgentLocator.getAgentJarPath();
        params.getVMParametersList().add("-javaagent:" + agentPath + "=com.example.app");
    }
}
XML plugin.xml — Déclaration de l'Extension Point 
<extensions defaultExtensionNs="com.intellij">
    <java.programPatcher
        implementation="fr.monequipe.sae.dynamic.AgentProgramPatcher"/>
</extensions>
